# 视频对应与差异分析：技术选型记录

调研日期：2026-10-04。工作分支：`zhangjy/video`。状态：**设计研究，未实现视频插件，未运行视频准确率或性能实验**。核心场景是同一素材的剪辑、调色、压缩和加字幕版本；不是搜索全网视频，也不把相似题材误称为相同素材。

## 推荐方向

先交付好用的原生只读视频比较：双画面、共同播放控制、逐帧查看、手动时间偏移与局部范围、并排／擦拭／叠加；再加入有证据、可拒绝、可修改的自动片段对应。默认不放专业评分仪表盘。用户首先要看见变化，而不是理解算法参数。

技术上优先复用 **AVFoundation / Core Media + 已有 OpenCV + 已有 Olaf helper**。初版无需新增大模型、Python、Java 或 FFmpeg。引入额外库必须由可测量的需求驱动；下面推荐流程是 CrossDiff 的工程判断，不是现成库已承诺的完整能力。

## 必须分开的三个问题

| 问题 | 输出 | 不能混淆的内容 |
| --- | --- | --- |
| 时间对应 | 左右时间范围、范围内的映射、锚点与证据 | 相同的播放秒数不代表相同镜头；同一配乐不代表相同画面。 |
| 空间对齐 | 已配对画面的平移／缩放／旋转、有效交集 | 找到对应帧后才能处理裁剪；配准不应自动抹掉用户想看的构图变化。 |
| 差异展示与质量分析 | 色彩／结构变化、叠加图、可选客观指标 | 相似度不是“画质分数”；调色后更不同不代表变差。 |

例如，右片头增加 3 秒，随后删除中间 5 秒，需要至少两段时间关系；只加一个全局 `+3 s` 偏移会在删除点之后再次错位。左侧 `A–B–C`、右侧 `C–A–A` 必须允许重排与重复关系，不能强制得到覆盖全片的一条单调路径。已有[音频局部对齐研究](audio-local-alignment.md)同样记录了这个边界。

建议数据模型预留多段关系，每段保留左右原始时间范围、对应锚点、来源（手动／声音／画面／联合）、分析覆盖范围和候选状态。未匹配、未分析、已确认仅左侧／仅右侧应分别建模，避免算法没找到便显示“确定删除”。

## 时间必须来自视频本身

Core Media 提供帧的 presentation timestamp（PTS）；它与 decode timestamp 不等同。内部使用 `CMTime` 和真实采样时间，不用 `frameIndex / nominalFrameRate` 作为 VFR 视频的真实时间。[Apple 时间与媒体表示](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/AVFoundationPG/Articles/06_MediaRepresentations.html)、[PTS API](https://developer.apple.com/documentation/coremedia/cmsamplebuffergetpresentationtimestamp(_:))

缩略图可用 `AVAssetImageGenerator` 并允许适量时间容差；精确停帧则把前后容差设为零，并记录返回的实际时间。Apple 明确指出零容差可能增加解码延迟，不能把拖动时的近似缩略图冒充已精确比较的帧。[Apple 时间容差](https://developer.apple.com/de/documentation/avfoundation/avassetimagegenerator/requestedtimetoleranceafter)

**实现推论：** 概览抽样与精确比较应是两条调度通路。连续分析使用 `AVAssetReader` 顺序解码并保留时间戳；停止拖动后再提升当前帧精度。帧间跳转选择前／后实际样本，不简单加减 `1/30`。29.97、23.976、VFR、非零起始 PTS、重复帧和不同帧率都要纳入测试。不同帧率时允许一个源帧对应对侧多个采样，不承诺逐帧一一对应。

画面旋转元数据也要统一处理。`appliesPreferredTrackTransform` 默认关闭，Apple 此接口支持 90／180／270 度旋转；设置 composition 时另按 composition 处理。缩略图、播放画面和分析坐标必须遵循同一种方向约定。[Apple 方向变换](https://developer.apple.com/documentation/avfoundation/avassetimagegenerator/appliespreferredtracktransform)

## 自动对应：分层候选，而不是两两穷举

### 第一条线：已有音轨指纹

当前仓库已固定 Olaf 源码提交 `a98d8c03cfd447011d402718ca2d10b2bb467eb0`。`AudioMatchingEngine` 接受 Apple 解码的 16 kHz 单声道 Float32 PCM，通过独立 helper 输出有界片段候选。现有集成限制包括每侧最长两小时、最多 512 个候选、宿主 120 秒超时；固定速度同源片段是当前支持范围，变速／变调并未承诺。[本项目依赖与边界](../../ThirdParty/AudioMatching/README.md)、[锁定来源](../../ThirdParty/AudioMatching/source-lock.json)、[宿主接口](../../Sources/CrossDiff/AudioMatchingEngine.swift)

Olaf 是内容指纹引擎，解码在它之外完成。因此视频不需要调用上游命令行工具或额外捆绑 FFmpeg：用 Apple 提取被选中的音轨，再适配现有 helper。音轨在 asset 中的起点、空洞、编辑时间映射需保留，不能把 PCM 从零开始的时间直接当视频时间。[Olaf 官方实现与限制](https://github.com/JorenSix/Olaf)

音频输出只提供候选时间关系。静音、换配乐、旁白替换、同一首歌被用于不相关画面时，应转向视觉证据；相同背景音乐不能独立确认视频镜头对应。多个音轨提供选择；默认处理选中的可听音轨，不把多语言音轨混成一种证据。

### 第二条线：视觉候选与多帧验证

建议由粗到细：

1. 按时长控制稀疏抽样数量，额外保留镜头变化附近样本。先做时间邻域／音轨候选中的搜索；无声音时再扩大视觉搜索。
2. 全局外观用于便宜的候选筛选：现有 OpenCV `calcHist`／`compareHist` 可作实验基线，但颜色分布会被调色改变，也会把不同场景误配，不能独自定案。[OpenCV 直方图比较](https://docs.opencv.org/4.12.0/d8/dc8/tutorial_histogram_comparison.html)
3. 可选增加 `opencv_contrib/img_hash` 的 pHash，替代自行实现感知哈希。**该模块当前不在构建列表中**；也不能把哈希当成耐裁剪、旋转、字幕覆盖的保证。它只适合作快速候选入口，并保留另一条局部特征召回通路。[OpenCV 图像哈希模块](https://docs.opencv.org/4.12.0/d4/d93/group__img__hash.html)
4. 候选帧用已有 SIFT／匹配／RANSAC 管线验证局部对应。OpenCV 提供局部特征匹配及稳健几何估计；CrossDiff 已有相似变换实现，不必为视频另写底层矩阵算法。[OpenCV 特征与几何验证](https://docs.opencv.org/4.12.0/d1/de0/tutorial_py_feature_homography.html)、[现有桥接](../../Sources/PhotoCVBridge/ImageMatchingBridge.cpp)
5. 在邻近多个时间点独立复核，并检查时间推进和几何关系是否一致；重复标题卡、黑场、静止镜头、相同角标不应仅凭一帧自动确认。只在候选范围内细化采样和边界；保持一对多候选，冲突交给用户选择。

“抽样帧检索 → 时间与空间一致性验证”有成熟研究基础。INRIA 的 TRECVID 系统以局部视觉特征、候选检索与时空验证组合处理视频副本；这支持架构方向，但不证明本项目尚未运行的实现已达到论文性能。[INRIA / NIST 原始报告](https://www-nlpir.nist.gov/projects/tvpubs/tv8.papers/inria-imedia.pdf)

**工程边界：** 第一阶段只自动接受固定速度的可靠局部对应；恒定速度变化另设下一阶段实验，非线性变速、倒放、复杂转场后置。跨片段不强制单调，但每个正常播放片段内部的时间映射应连续且单调。误配比“未找到”更破坏用户信任，不用未校准的百分数叫“置信度”。

### 成本与预算

两个一小时、30 fps 视频各有 108,000 帧，全部两两配对达到 **116.64 亿** 对；仅保存一个 Float32 分数矩阵就约 **46.7 GB**。即使降到 1 fps，两侧也有 1,296 万对。以上只是按维度计算，不是实测速度，尚不包含特征和解码。

首版应设抽样帧数、候选数、分辨率、内存缓存、时间与解码并发预算；分批索引、有限 top-k 候选、局部精修，避免整片稠密矩阵。粗采样可能漏掉很短的片段，要明确覆盖限制。缓存键包括源文件版本、选中轨道、解码方向／色彩设置、算法版本和参数；更换文件或取消时禁止旧任务覆盖新会话。

## 空间对齐不要隐藏真实修改

首版可直接复用图片的整体相似变换，但应为**当前对应片段**保存，而非给整个视频套一个未知是否有效的变换。时间对应后，用户可按需对齐裁剪或缩放，再通过擦拭查看剩余差异。

不要每帧无提示地重新估计并应用变换：估计抖动会造成画面跳动；自动补偿还可能把防抖、缩放和构图修改隐藏。默认显示原始构图，只在用户启用“空间对齐”后应用，并显示有效交集、随时恢复。交集之外标记为未覆盖，不能当成黑色像素参与差异评分。非平面、视角改变、运动主体与局部贴图无法保证由一个变换解释。

## 差异展示与专业指标的使用边界

建议默认只有双图和时间线。用户展开“分析”后显示当前帧／已确认片段的结果，避免加载文件便出现一个误导性的全片“相似度 93%”。

| 分析 | 建议实现 | 可说明什么 | 不应说明什么 |
| --- | --- | --- | --- |
| 擦拭、叠加、闪看、差异图 | 现有图片比较思想，Core Image／原生渲染 | 对应时刻哪里发生像素变化 | 哪个版本更优秀；自动识别修改原因。 |
| PSNR | 已有 OpenCV `cv::PSNR` | 同一像素定义与空间尺寸下的误差指标，单位 dB | 调色美学、素材同源概率。 |
| SSIM | `opencv_contrib/quality::QualitySSIM`，或后续 libvmaf | 对齐帧的结构相似及局部质量图 | 自动找到时间关系，或证明整片没有遗漏。 |
| VMAF | 官方 `libvmaf` C 库，后置可选分析组件 | 已选参考、时空对齐的压缩版本质量估计 | 给两个任意剪辑、不同调色或不同作品打高低分。 |
| 色彩分布／RGB 直方图 | 复用摄影插件的 Apple／OpenCV 管线 | 当前对应帧的影调与色彩变化 | 从成片反推确定的调色参数或拍摄曝光。 |

OpenCV 的 PSNR API 位于 core；`QualitySSIM` 属于额外 quality 模块，不能因为当前已链接 OpenCV 就假定该接口可用。优先调用正式库 API，不复制教学示例中的指标公式再由项目维护。[PSNR API](https://docs.opencv.org/4.12.0/d2/de8/group__core__array.html)、[QualitySSIM API](https://docs.opencv.org/4.12.0/d9/db5/classcv_1_1quality_1_1QualitySSIM.html)

Netflix 官方说明 libvmaf 同时提供 VMAF、PSNR、SSIM 等实现；官方计算示例强调时间戳同步和比较分辨率设置。[libvmaf](https://github.com/Netflix/vmaf)、[官方输入准备示例](https://github.com/Netflix/vmaf/blob/master/resource/doc/ffmpeg.md)

模型并非一个万能配置。2026 年的 VMAF v1 文档分别列出 1080p、Phone、4K 与 HFR 变体，并建议 SDR 分析采用适当的 10 位精度；不同模型的观看条件、分数范围不完全一样。因此未来界面必须显示实际模型／分析条件，不能默用一个模型解释所有视频。[VMAF 官方模型说明](https://github.com/Netflix/vmaf/blob/master/resource/doc/models_v1.md)

**色彩要求：** 分析路径保留色域、传递函数、YCbCr 矩阵、位深与范围；不能把两边各自 tone-map 后的屏幕截图当作原始视频质量输入。Apple 的 HDR 文档明确区分这些元数据。[Apple HDR 管线](https://developer.apple.com/videos/play/wwdc2020/10010/)。首版可交给原生播放处理支持的 HDR，但在没有验证统一 HDR 分析路径之前，明确标记高级数值分析未支持，而不是静默转成 SDR 后报“客观画质”。

PSNR／SSIM／VMAF 的前处理、分析分辨率、帧／片段范围、是否采样必须随结果保存。字幕、裁剪、色彩风格变化都是真实改动，不能自动排除以提高分数；ROI 或字幕区排除需显式操作。

## 依赖、许可与体积

| 组件 | 当前情况与选择 | 体积判断 |
| --- | --- | --- |
| Apple AVFoundation / Core Media / Core Image | 系统框架，不随插件复制框架；遵守 SDK 和平台 API 条件。 | 无需分发解码器或大模型权重，新增宿主代码大小仍须实际构建。 |
| OpenCV 4.12.0 | 已有 core、imgproc、features2d、calib3d、flann；Apache 2.0，保留本项目已有声明。[项目声明](../../ThirdParty/OpenCV/NOTICE.md) | 复用当前已链接功能，无额外模型下载；若新增 contrib 模块需单独测链接产物差额，不能拿源码包大小当应用增量。 |
| Olaf helper | 已有 AGPL-3.0-or-later 核心和各子依赖声明，继续固定来源及保留对应源码。[本项目声明](../../ThirdParty/AudioMatching/README.md) | 复用宿主 helper，不再随视频插件复制第二份；上游 WASM 大小不代表 macOS 原生产物大小。 |
| libvmaf | 当前未集成；BSD-2-Clause-Patent，保留许可与所选模型来源。[官方 LICENSE](https://raw.githubusercontent.com/Netflix/vmaf/master/LICENSE) | 可采用 C 库，不必捆绑 Python；本轮未做 arm64 裁剪构建，不报未经测量的 MB 数。 |

OpenCV contrib 的质量／哈希模块需要固定相同版本、完整检查实际依赖与许可证、在项目内编译，不引入 pip 或全局安装。专业分析后置并不要求“插件依赖另一个插件”：视频可使用宿主共享媒体服务，音频／图片插件只控制各自比较入口。现有插件机制能否承载独立下载的原生分析组件需按宿主契约实现，不能把一个 manifest 当成新增动态原生代码的能力。

Olaf 上游文档同时列有特定指纹技术的专利说明；保留其来源声明，不从“开源”外推所有使用场景的法律结论。本次未作法律结论。

## 建议里程碑与验收

| 阶段 | 用户可观察的交付 | 通过后再进入下一步 |
| --- | --- | --- |
| V1 原生比较 | 本地双视频、联动／独立浏览、帧步进、共同播放控制、单侧声音切换、手动偏移与对应范围、擦拭／叠加、局部放大 | 实际帧时间可核对；不同长度／方向／帧率不会隐式错配；浅深色、最小窗口清晰；长视频不一次载入内存。 |
| V2 辅助匹配 | 显式“查找对应片段”；固定速度音频候选 + 视觉复核；候选确认／撤销；重复与重排表示 | 负样本拒识、多候选不强行选唯一、取消及时、分析覆盖明确。 |
| V3 深入分析 | 独立视觉检索、局部恒定变速实验、可选 SSIM／VMAF、片段差异摘要 | 真值与前处理可追溯；报告不把采样当全帧；无效输入不输出伪分数。 |

V1 的手动时间锚点设计应预留扩展为多个片段；不一定首版就把复杂片段编辑器全部展示出来。快捷操作保持“暂停到这一帧 → 两边调到同一画面 → 设为对应”即可理解。

推荐使用项目内生成、来源可控的测试素材并保留真值时间映射：

- 同素材无改动、不同容器／编码、码率／分辨率变化、色彩调整、加字幕／水印、裁剪、旋转。
- 加片头、单次删除、多次剪切、片段重排、重复插入；渐隐／叠化和过短镜头单列。
- 同画面换配乐、同配乐换画面、静音、双声道反相、多音轨、音轨非零起点。
- 黑场、白场、静态幻灯片、重复标题、周期运动、相似场景不同 take，以及完全不相关视频。
- 23.976／29.97／60 fps、VFR、丢帧／重复帧、恒定变速与变速坡道；竖屏方向元数据；SDR／HDR 不混算。
- 1080p／4K 长文件的首次预览延迟、缓存上限、取消延迟、峰值内存和后台恢复；损坏文件、资源预算耗尽、文件外部改变。

自动匹配分别记录片段召回、错误对应、起止时间误差、重复候选保留及耗时／内存；不能只用几张成功截图验收。帧级分析记录实际左右 PTS 和空间覆盖，保证用户复现同一对画面。本轮只完成上述来源与代码核查，应用实现和原生视频验收尚待后续研发。
